> **Status:** Living document. **Everything in the audit + all follow-ups is implemented.** Note on the CRDT choice: structured data (the spec) uses Liveblocks **Storage** (LiveMap/LiveObject) — the right primitive here. **Yjs** is for *rich-text* CRDTs (the documents editor uses it via Tiptap); it would be the wrong tool for a structured step graph. Further refinement possible: per-field merge *within* a step (today a single step's config is whole-step replace), and Liveblocks-native undo/redo (today the custom history stack writes reverted specs into Storage, which works but isn't per-user).

> Note on migrations & HTTP: the version-history and optimistic-locking features needed **no new migration** — migration 0026's `workflow_versions` / `workflows.current_version_id` already had the columns. The HTTP action needs **no external provider** — the server makes the request via `fetch`; the step just exposes it configurably. Email/Telegram/WhatsApp need env vars: `RESEND_API_KEY` + `RESEND_FROM_EMAIL`, `TELEGRAM_BOT_TOKEN`, `WHATSAPP_TOKEN` + `WHATSAPP_PHONE_NUMBER_ID`.

## Executive summary

This is an ambitious, thoughtfully-architected workflow editor that is roughly 70% of the way to a credible Zapier/Make-class product for non-technical hotel staff — but it ships two divergent canvas implementations of the same spec, one of which (the "Map" / xyflow view) is fundamentally broken for authoring: adding a step produces an orphan node that never executes (workflow-canvas.tsx:242-263), and deleting a step severs the chain instead of splicing it (graph.ts:339-376). The "Steps"/Flow view is the genuinely strong surface (correct splicing insert/delete, branch lanes, plain-English summaries, inline validation, a polished palette), and the spec/validation/catalog layers are well-factored. The standout strengths are the no-magic-strings data picker, the shared plain-English explanation engine, and the humanizeStepError observability layer. But the editor falls short of industry expectations in five load-bearing ways: (1) no undo/redo anywhere, which is the single biggest forgiveness gap for the target persona; (2) no real test/dry-run despite dryRun being fully plumbed through every runner — the only "test" path fires real side effects; (3) the AI authoring loop has unrecoverable dead-ends (propose_entity_type strands the user with no spec and no button; starter-prompt clarifications vanish into a toast); (4) the run inspector promises detail the engine never writes (ai_trace, error_step_id, per-step durations, "waiting" status all empty/meaningless); and (5) the condition builder cannot express the AND/OR-of-groups, date comparisons, or "contains" that real hotel automations need, silently dropping users into a read-only JSON dead-end.

The most urgent work is correctness, not features: the Map view will corrupt workflows, autosave can silently stop persisting with misleading "Fix the errors above" guidance when no error is visible (e.g. disconnected trigger, builder-shell.tsx:95,293-296), the runtime throws on JSON-mode conditions the builder happily saves (predicate.ts:26-28,69-70), and every cosmetic node drag spawns a new immutable version (save.ts:42-43). My recommendation: either fix or hide the Map view immediately, add undo + a safe dry-run + a beforeunload guard, close the AI dead-ends, and wire the observability fields the inspector already renders. The foundations are good enough that these are mostly fills rather than rewrites.

## Strengths

- **No-magic-strings data mapping** — The TemplateField + Insert-data popover (template-field.tsx) hides {{dotted.path}} entirely: pure refs render as friendly removable chips, mixed text shows readable 'includes' pills, and the picker is grouped-by-source and searchable with sample values (refs.ts availableRefs). This matches the single most important industry UX pattern (Zapier/Make/n8n pills over raw syntax) and the codebase gets it right.
- **Shared plain-English explanation engine** — explain-expr.ts + catalog explain() summarizers render every predicate and step into one human sentence reused across canvas cards, branch lane headers, and the inspector ('Only continue if priority is urgent', 'Draft a warm reply to …'). This is the inline-summary affordance that mature editors use to make complex flows scannable, and it is consistently applied.
- **Flow view splicing correctness** — The Steps/Flow view (tree-list.tsx) does control-flow mutation correctly: insertStep threads the displaced step onto the new step's .next and seeds branch lanes with End terminuses (tree-list.tsx:238-304), and deleteStepSpliced reconnects references and substitutes fresh End nodes for emptied lanes (tree-list.tsx:1490-1539). This is the polished, correct authoring surface.
- **Thoughtful multi-pass validator** — validate.ts runs Zod parse + catalog membership + reachability-aware ref checking (a ref is valid only if its source step is in the BFS upstream ancestor set) + scope-aware predicate validation, returning a flat path-addressed issue list rendered inline on cards rather than throwing (validate.ts:291-297, predicate-vars.ts). Reachability-aware ref checking is more rigorous than most no-code tools.
- **Plain-English error humanization in the run inspector** — humanizeStepError() (run-inspector-client.tsx:268-294) translates known runtime messages into plain language for non-technical operators, paired with a live Supabase-Realtime tail of runs and steps. This is exactly the 2025-26 bar for non-technical debuggability and is the strongest part of the observability story.
- **Catalog as a coherent metadata vocabulary** — The catalog (lib/workflows/catalog/*) cleanly separates label/description/examplePrompts/outputSchema/explain per trigger and step, is client-safe, and drives the AI author bot's vocabulary, the data picker, and the inspector forms from one source. 18 triggers + ~30 steps across 9 surfaces is solid breadth for internal CRUD.
- **AI-first authoring on-ramp** — The copilot turns plain-English goals into a validated WorkflowSpec rendered live, supports multi-turn refinement via currentSpec round-trip, offers clarification chips, and has cross-surface ?prefill entry from kanban/task/chat (new-workflow-client.tsx:32-46). The Describe→Refine architecture is the right modern pattern even though the loop has holes.

## Prioritized gaps

Severity × effort, grouped by category. Effort: S = hours/small, M = days, L = a project.

### actions

#### [HIGH · L] No outbound/integration primitives (HTTP, webhook, email, SMS, transform/formatter)

- **What exists:** ~16 internal-surface CRUD actions across tasks/chat/docs/meetings/entities plus notify and gbrain.capture. Surface type reserves 'external'; delegate_to_openclaw is a logging stub.
- **What's missing:** No HTTP request, call webhook, send email, send SMS, or data-transform/formatter step. A hotel automation that must hit a PMS/booking API, post to a Slack webhook, email a guest, or reformat a date/number has no path except an unbuilt Tier-2 service.
- **User impact:** The single biggest capability gap for real-world automations. Also: zero transform layer means trivial date/text/number reformatting (the most-requested mapping need in every competitor) is impossible.
- **Evidence:** `lib/workflows/catalog/system.ts:100-112; lib/workflows/catalog/index.ts:29-38; field-defs.ts (no formatter)`

#### [MEDIUM · M] Asymmetric surface coverage hints at capabilities that don't exist

- **What exists:** calendar has 2 triggers but 0 actions; docs can create/archive but not update/append; tasks can add_label but not remove.
- **What's missing:** No create/update/cancel calendar event, no doc append/update, no remove-label or task comment. A user who sets up 'when a conflict is detected' or 'when label added' discovers mid-build they can't take the natural follow-up action.
- **User impact:** Common flows ('block the GM's calendar', 'append shift notes', 'remove the urgent label once resolved') are impossible, and the trigger presence implies an action that isn't there.
- **Evidence:** `lib/workflows/catalog/index.ts:13; lib/workflows/catalog/calendar.ts; docs.ts:28-71; tasks.ts:148-161`

### authoring

#### [CRITICAL · M] Map view 'add step' creates an orphan node that never executes

- **What exists:** The Steps/Flow view splices new steps into the chain correctly (tree-list.tsx:238-304). The Map/xyflow view has its own addStepAt that writes the step into spec.steps + spec.layout and sets entry_step_id only if previously empty.
- **What's missing:** addStepAt (workflow-canvas.tsx:242-263) never threads the new step onto any parent's .next, a branch slot, or anything. Clicking or dragging a palette step into a non-empty workflow produces a disconnected node unreachable from the trigger — no auto-drawn edge, no warning.
- **User impact:** A non-technical user building visually in Map mode assembles a workflow that silently drops every step after the first. The orphan node looks identical to a wired one. This is data corruption presented as success.
- **Evidence:** `components/workflows/builder/canvas/workflow-canvas.tsx:242-263 vs tree-list.tsx:238-304`

#### [CRITICAL · M] Map view delete severs the chain instead of splicing it

- **What exists:** Flow view's deleteStepSpliced reconnects references to the victim's .next and substitutes End nodes (tree-list.tsx:1490-1539).
- **What's missing:** Map view routes deletes (node 'remove' change and the wf-node toolbar) to graph.removeStep, which sets predecessors' .next to undefined and strips branch keys entirely (graph.ts:339-376) rather than reconnecting to the victim's successor. Deleting a mid-chain step disconnects everything after it; deleting a branch target removes the lane.
- **User impact:** The same delete gesture yields opposite results depending on which tab the user is in. A user who learns the Steps-view mental model gets burned switching to Map — their flow silently breaks.
- **Evidence:** `lib/workflows/graph.ts:339-376 vs components/workflows/builder/tree-list/tree-list.tsx:1490-1539`

#### [CRITICAL · M] AI 'propose_entity_type' is an unrecoverable dead-end

- **What exists:** The author bot's propose_entity_type tool stops without emitting a workflow and narrates 'Proposed new entity type: Rooms'. AiCopilot has an optional onProposedEntityType callback.
- **What's missing:** No parent ever supplies onProposedEntityType — new-workflow-client.tsx, builder-shell.tsx's Flow copilot, and the WorkflowCanvas pass-through (workflow-canvas.tsx:438) all receive undefined. When a user asks for any room/guest/booking automation (exactly the hotel cases the persona is told to reach for), they see only a narration line, no spec, and no button to create the entity or continue.
- **User impact:** The first-run user hits a wall with zero recovery on the most common hotel use-cases. The AI appears to have silently failed.
- **Evidence:** `lib/ai/bots/workflow-author-bot.ts:257-269; ai-copilot.tsx:133-144; new-workflow-client.tsx:118-124; builder-shell.tsx:217-228,255-262`

#### [HIGH · L] No undo/redo anywhere in the builder

- **What exists:** Every mutation (insert, delete, reorder, drag, connect, disconnect, auto-layout, AI-apply) calls setSpec/onChange directly. There is a savedSpec baseline used by rejectAll.
- **What's missing:** No history stack, no Cmd-Z handler in either canvas file. onAutoLayout destructively strips spec.layout with no confirmation (workflow-canvas.tsx:317-323). An AI-applied spec, a mis-drag, or an accidental delete has no on-canvas recovery.
- **User impact:** For non-technical hotel staff this is the single biggest forgiveness gap — every leading editor (n8n, Make, Power Automate) ships Cmd-Z. A misclick or a bad AI refinement is unrecoverable without re-authoring.
- **Evidence:** `components/workflows/builder/canvas/workflow-canvas.tsx:317-323; components/workflows/builder/tree-list/tree-list.tsx:306-312`

#### [HIGH · M] Starter prompts and ?prefill swallow clarifications and entity proposals

- **What exists:** The full AiCopilot handles clarification chips and currentSpec round-trip. The new-workflow screen's three curated starter prompts and cross-surface ?prefill use a separate hand-rolled sendStarter fetch.
- **What's missing:** sendStarter (new-workflow-client.tsx:169-195) handles only 'spec'/'error'/'clarification' (the last as a fleeting toast), ignores propose_entity_type, and sends no conversation and no currentSpec — so a clarification can never be answered. The headline first-run CTA can produce a transient toast and an unchanged blank screen.
- **User impact:** The single most prominent zero-to-one path can dead-stop. A user clicking 'When a task labeled guest-complaint is created…' that triggers a clarification has no way to respond.
- **Evidence:** `app/p/[propertyId]/workflows/new/new-workflow-client.tsx:169-195,32-46`

#### [HIGH · S] No inline required-field feedback in the inspector

- **What exists:** TypedStepForm renders a red asterisk for required fields. builder-shell's computeInvalid surfaces required-field errors on the collapsed canvas card.
- **What's missing:** The asterisk is decorative — no aria-invalid, no red border, no inline 'X is required' on the field itself (typed-step-form.tsx:95-99). A user who blanks a mandatory field gets zero feedback inside the inspector; they must close it and spot a badge on the card.
- **User impact:** Violates the forgiving/clear goal for non-technical users — they cannot tell, while editing, that the field they just blanked is mandatory.
- **Evidence:** `components/workflows/builder/canvas/typed-step-form.tsx:95-99; builder-shell.tsx:275-289`

#### [HIGH · M] Config silently degrades to raw JSON as the catalog grows

- **What exists:** STEP_FIELDS drives friendly forms for hand-authored step types; the inspector falls back to a JsonEditor for any type without an entry.
- **What's missing:** STEP_FIELDS is a Partial map and does not derive fields from the Zod schema in spec.ts. ai.extract_fields has no entry at all; control.filter/branch_if have none. New catalog actions without a hand-written field-def show hotel staff a bare JSON textarea ('No friendly form yet… edit raw JSON', node-inspector.tsx:653-665).
- **User impact:** A scaling cliff: every catalog addition needs a parallel manual field-def or the UX collapses to unusable JSON for the target persona.
- **Evidence:** `node-inspector.tsx:653-665; field-defs.ts:103`

#### [MEDIUM · M] AI Accept/Reject gate is cosmetic and Reject discards human edits

- **What exists:** AI-added step ids are tracked as 'unaccepted' and shown in an AcceptBar with Accept all / Reject.
- **What's missing:** Autosave keys off validity, not acceptance, so AI-added steps are persisted before the user accepts (builder-shell.tsx:90-102). Accept all merely clears the set without saving. Reject reverts the ENTIRE spec to savedSpec (builder-shell.tsx:145-149), discarding any human edits made since the last save — not just the AI's additions.
- **User impact:** The accept gate doesn't actually gate persistence as the UI implies, and 'Reject' silently destroys the user's own unrelated edits.
- **Evidence:** `components/workflows/builder/builder-shell.tsx:90-102,136-149`

### collaboration

#### [HIGH · M] No concurrency control — last write wins, silently clobbering a concurrent editor

- **What exists:** saveWorkflow computes nextVersion from the latest version row and updates by id+property_id.
- **What's missing:** No optimistic-lock / expected-version check (save.ts:46-75,94-100). The client never sends a base version; the server never compares one. Two editors — or a forgotten background tab whose autosave fires — overwrite each other with no conflict detection.
- **User impact:** For a multi-staff product, edits are lost silently. A stale tab can clobber fresh work.
- **Evidence:** `lib/workflows/save.ts:46-75,94-100`

### data-mapping

#### [HIGH · L] Loops/parallel are effectively un-authorable through the friendly UI

- **What exists:** control.foreach (item_var, body_start) and control.parallel (branches) exist in the spec and durable runtime.
- **What's missing:** (1) foreach/parallel forms ask users to type snake_case step reference names as free text with no picker and no existence check (field-defs.ts:634-678). (2) buildUpstreamMap never follows body_start or parallel.branches (validate.ts:255-264), so a step inside a loop body gets no upstream refs AND there is no ref candidate for the per-item value anywhere in refs.ts — 'for each action item, create a task' cannot pick the current item. (3) extract_fields output is an opaque json blob in the picker (ai.ts:67-69, refs.ts), so its whole purpose is defeated.
- **User impact:** The most powerful primitives (loops, parallelism, per-item mapping, field extraction) are gated behind internal knowledge the UI otherwise hides, and the data picker can't reference loop items or extracted fields at all.
- **Evidence:** `field-defs.ts:634-678; validate.ts:255-264; refs.ts:220-240; lib/workflows/catalog/ai.ts:67-69`

#### [MEDIUM · S] Enum/number/duration field defaults shown-but-not-persisted; duration silently destroys unrecognized values

- **What exists:** Typed fields render defaults as selected and autosave on change.
- **What's missing:** Enums/numbers with a default render as selected but never write to config until clicked (typed-step-form.tsx:188-189,228-229) — the saved spec omits the key and the displayed state diverges from stored state. DurationField parses only \d+(s|m|h|d); a stored '1h30m', '1w', or templated value renders blank and the next keystroke overwrites it with no warning (typed-step-form.tsx:307-346).
- **User impact:** Users believe they set priority/length/max_steps but config stores nothing; and a non-conforming duration is silently lost — confusing if they later inspect runs or raw JSON.
- **Evidence:** `typed-step-form.tsx:188-189,228-229,307-346`

#### [MEDIUM · M] Picker samples and refs are static / under-report the real trigger payload

- **What exists:** refs.ts surfaces curated trigger fields with static sample values; the picker is grouped and searchable.
- **What's missing:** Samples are hardcoded, not pulled from a real recent run (the industry's most important mapping UX). TRIGGER_FIELDS is hand-curated and incomplete — doc/meeting/calendar/entity triggers expose only id-level fields though their catalog outputSchemas advertise richer payloads (refs.ts:105-111 vs meetings.ts:30-35, entities.ts:42-50). No live resolved-value preview of a configured field.
- **User impact:** Users map confidently against samples that may not match production shape, and the picker silently omits fields the trigger actually provides, forcing them to free-type paths the UI was designed to hide.
- **Evidence:** `lib/workflows/refs.ts:105-111; catalog/meetings.ts:30-35; catalog/entities.ts:42-50`

### error-handling

#### [MEDIUM · M] wait_for_event has no timeout enforcement — runs can hang forever

- **What exists:** control.wait_for_event reads cfg.timeout and awaits a durable hook resumable by an external event.
- **What's missing:** cfg.timeout is read but never used (durable-runtime.ts:388-425) — there is no race against a sleep, no transition to a 'waiting' status, and no cancel. If the correlated event never arrives, the run waits indefinitely and shows 'running' forever.
- **User impact:** A non-technical user cannot distinguish a hung run from a slow one, has no countdown or cancel, and the workflow is stuck permanently.
- **Evidence:** `lib/workflows/durable-runtime.ts:388-425`

#### [MEDIUM · M] Retry and on-error are absent from the configuration UI

- **What exists:** spec.ts defines per-step retry (max/backoff/initial_ms) and on_error (fail/continue/branch); both runtimes honor them.
- **What's missing:** No STEP_FIELDS surface retry or on_error for any step (field-defs.ts). A non-technical user cannot configure 'retry 3 times' or 'on error continue' through the friendly form even though the runtime fully supports it.

### logic

#### [HIGH · S] Runtime throws on JSON-mode conditions the builder happily saves

- **What exists:** The condition builder degrades any predicate it can't model flat to a read-only 'Custom condition' JSON view, preserving it. The runtime evaluator supports a small operator set.
- **What's missing:** predicate.ts throws on any object with !=1 key (predicate.ts:26-28) and any unrecognized operator (predicate.ts:69-70). A 'Custom condition' using a standard jsonlogic op (cat, if, %, 3-arg comparison) saves fine but hard-throws at dispatch/filter time. A workflow can be saved in a state that crashes when it fires.
- **User impact:** A user who pastes or inherits a slightly-complex condition saves successfully, then the workflow silently crashes at runtime (dispatcher catches it as 'runtime_error' and the workflow never runs, with no run row).
- **Evidence:** `lib/workflows/predicate.ts:26-28,69-70`

#### [HIGH · L] Condition builder cannot express AND/OR-of-groups, date comparison, or 'contains'

- **What exists:** A flat ALL/ANY list of Field·Operator·Value rows with type-aware operators, enum dropdowns, and 'is any of'.
- **What's missing:** No nested groups / mixed AND-OR ('priority is urgent AND (status is todo OR blocked)') — any nesting drops to read-only JSON (jsonlogic-codec.ts:37-40,83-95). No date comparison: due_at/fired_at are typed 'string' (refs.ts:91,113-119) so they only get is/is-not, and numeric > coerces with Number() yielding NaN-false on ISO strings (predicate.ts:43-54) — 'due date before X' is literally unbuildable. No 'contains'/'starts with' for free text despite the runtime's 'in' supporting substring.
- **User impact:** Real hotel automations need grouped logic, date filters, and text-contains (e.g. 'message contains refund'). Hitting any of these silently forces the non-technical user into a JSON view they were explicitly designed never to see, with only 'Clear and start over' as an escape.
- **Evidence:** `lib/workflows/jsonlogic-codec.ts:37-40,83-95; refs.ts:91,113-119; predicate.ts:43-54`

#### [MEDIUM · M] Validation never flags cycles, orphans, or dangling control-flow targets

- **What exists:** Reachability-aware ref checks and next/branch/on_error target-existence checks.
- **What's missing:** No cycle detection or orphan-step error (validate.ts:232-267). foreach.body_start, parallel.branches[], and branch_switch keys are not existence-validated against spec.steps (validate.ts:94-115), and removeStep never rewrites a body_start/branch pointing at a deleted step. A switch with no _default dead-ends at runtime with no warning.
- **User impact:** A workflow with a loop, a stranded sub-chain, or a dangling foreach body validates 'ok' and saves; part of the flow silently never runs and the executor's cycle behavior is undefined.
- **Evidence:** `lib/workflows/validate.ts:94-115,232-267; lib/workflows/graph.ts:339-376`

#### [MEDIUM · S] 'is empty' / numeric operators contradict their English label

- **What exists:** 'is empty' emits {not:{var}}, 'is not empty' emits {'!=':[var,'']}, offered for number and boolean types too.
- **What's missing:** For a number field with value 0, {not:{var}} is true so 'is empty' matches a present zero, contradicting the reassuring help text 'this just checks whether the field is filled in' (condition-builder.tsx:814-818). A freshly added boolean clause shows 'Yes' but serializes to false until re-selected.
- **User impact:** The builder produces conditions that evaluate opposite to what the plain-English label promises, with no warning — a silent correctness trap for non-technical users.
- **Evidence:** `lib/workflows/jsonlogic-codec.ts:58-63,187-189; condition-builder.tsx:814-818,924-936`

#### [MEDIUM · M] parallel join:'any' leaks losing branches' side effects

- **What exists:** control.parallel with join:'any' uses Promise.race to merge the winner's outputs.
- **What's missing:** Losing branches keep executing in the background (durable-runtime.ts:493-520); their step rows persist and their side effects (task creation, messages) still fire. No cancellation of losers.
- **User impact:** A user choosing 'any' to mean 'whichever finishes first' gets duplicate/unexpected side effects from the slower branches.
- **Evidence:** `lib/workflows/durable-runtime.ts:493-520`

## Industry feature benchmark

What a best-in-class workflow editor offers, from the research pass. Use as a checklist.

### Workflow/Automation Editor — Trigger Capabilities

Research on best-in-class trigger capabilities across Zapier, Make, n8n, Workato, Pipedream, Microsoft Power Automate, and Temporal (2025-2026). The canonical mental model is that every workflow begins with exactly one trigger node that defines HOW a run starts. The mature platforms converge on a small set of trigger *families* — event/app triggers (instant + polling), schedule/cron, inbound webhook (catch hook), manual/on-demand, and form/chat — and then differentiate on the *quality of the trigger runtime*: per-trigger filter conditions that short-circuit before consuming run quota, robust deduplication (unique-key cursors / high-watermarks), fan-out control (split-on / batch / single), concurrency control, replay/reprocessing of past trigger events, and a strong build-time UX (pull a live sample, see the exact payload shape, test the filter against that sample before publishing).\n\nKey UX patterns that separate a polished editor from a toy: (1) instant-vs-polling is surfaced as a visible badge on the trigger with an explanation of latency, not hidden plumbing (Zapier 'Instant' badge, Make 'instant' label); (2) the trigger setup wizard fetches a *real* recent record so downstream steps map against live data, with a 'pull more samples' button; (3) deduplication is automatic by default but exposes a configurable unique-key field for sources whose payloads lack an 'id'; (4) cron is offered as both a friendly recurrence builder (every N min / daily at / weekly on) AND a raw cron expression with a human-readable 'next 5 runs' preview; (5) webhook triggers display the generated URL, sample curl, and a live 'listening…' capture mode; (6) filter conditions live ON the trigger (trigger conditions) so noisy events never start a run and never burn quota. Differentiators in 2025-2026: durable wait-for-event mid-workflow (Temporal Signals, signal-with-start), schedule-as-first-class-object decoupled from the workflow (Temporal Schedules, paused/backfilled independently), event replay, AI/chat triggers, change-data-capture triggers, and multi-trigger workflows (multiple entry points into one graph).\n\nCommon pitfalls: treating instant and polling as the same thing (they have different dedup semantics — Zapier does NOT dedupe instant triggers, the sender must); forgetting fan-out semantics (one array event vs N separate runs); no concurrency control leading to race conditions; cron without timezone handling; webhook triggers without verification/secret; running filters AFTER the run already started (wastes quota) instead of as a true trigger condition; and missing replay/backfill so a misconfigured trigger loses events permanently.

**Must-have**

- **Single designated trigger node as the workflow's entry point** — Every mature editor models a workflow as 'one trigger → graph of actions'. The trigger node is visually distinct (rounded/colored, lives at the top/left) and choosing it is step one of building. n8n enforces this (you cannot add a second Manual Trigger); Zapier/Make/Power Automate force you to pick a trigger before any action exists. Without a clear single entry point the run semantics are ambiguous. _(seen in: Zapier, Make, n8n, Power Automate, Pipedream, Workato)_
- **App/event triggers with instant (webhook-backed) delivery and a visible 'Instant' indicator** — The highest-value triggers fire the moment something happens in a connected app (new row, new message, status change) via the vendor's outbound webhook. Best practice surfaces this as a badge ('Instant' in Zapier, 'instant' in Make, '(Instant)' suffix on Pipedream sources) plus a one-line latency explanation, so users understand they're not waiting on a poll. Instant triggers run regardless of plan-level poll interval. _(seen in: Zapier, Make, n8n, Pipedream, Workato, Power Automate)_
- **Polling triggers with a configurable/plan-tiered interval as a universal fallback** — Most app triggers are polling — the engine does a periodic GET against the app's API and diffs the result. This works with virtually any API even when the app offers no webhook. UX must communicate the interval (Zapier: 1–15 min by plan; n8n: ~every minute; Make Watch modules) because it sets the latency expectation and, on usage-metered platforms, every empty poll can cost an operation. A polished editor lets self-hosted/advanced users tune the interval. _(seen in: Zapier, Make, n8n, Workato, Power Automate)_
- **Inbound webhook / 'catch hook' trigger with auto-generated URL, sample payload capture, and method selection** — A generic HTTP trigger lets ANY external system start a workflow. The expected UX: generate a unique URL, show a copyable curl example, offer a live 'listening for request' capture so the user fires a test and the real payload is captured for downstream mapping, and let the user pick HTTP method (GET/POST/PUT/PATCH/DELETE) and a response mode. n8n's Webhook node, Make Custom Webhooks, Pipedream HTTP trigger, Zapier Catch Hook, and Power Automate's HTTP request trigger all do this. _(seen in: n8n, Make, Pipedream, Zapier, Power Automate)_
- **Schedule/cron trigger with both a friendly recurrence builder and raw cron, plus timezone + 'next runs' preview** — Time-based runs are table stakes. Best-in-class offers a dual UX: a no-code recurrence builder (every N minutes/hours, daily at HH:MM, weekly on selected days, monthly on date) AND a raw cron expression field for power users, with explicit timezone handling and a human-readable 'next 5 executions' preview so users catch mistakes before publishing. n8n's Schedule node and Pipedream's scheduler exemplify the dual mode. _(seen in: n8n, Make, Pipedream, Power Automate, Zapier, Temporal)_
- **Manual / on-demand trigger for building, testing, and ad-hoc runs** — An 'Execute Workflow' / 'Run once' button is essential during authoring so users see real data flow through downstream nodes without waiting for a real event. Power Automate elevates this to a first-class flow type ('instant cloud flow' triggered by a button, including a mobile button). n8n's Manual Trigger is the default while building. Mature editors also support manual run with custom input payloads. _(seen in: n8n, Power Automate, Zapier, Make, Temporal)_
- **Build-time sample fetch: pull a real recent record to define the downstream data shape** — This is the single most important *UX* pattern. When configuring the trigger the editor calls the app and returns one or more real recent records ('Test trigger' in Zapier shows representative records; n8n 'fetch test event'). Downstream steps map fields against this concrete sample, and a 'pull more samples' affordance lets users page to a record that has the fields they need. Without live samples, field mapping is guesswork. _(seen in: Zapier, n8n, Make, Pipedream, Workato)_

**Standard**

- **Trigger filter conditions (pre-run gating) that short-circuit before a run starts** — Conditions evaluated AT the trigger — not as a first action — prevent noisy events from ever starting a run, which saves quota/operations and avoids race conditions. Power Automate's 'trigger conditions' (advanced expression that must be true) is the gold standard; Zapier's Filter step + day/time filters and Workato's trigger conditions serve similarly. Best UX tests the condition against the captured sample and tells you 'would have continued / would have stopped' immediately. _(seen in: Power Automate, Zapier, Workato, Make, n8n)_
- **Deduplication with automatic unique-key cursor/high-watermark + configurable dedupe key** — Polling triggers must not re-fire on records already seen. The engine tracks a cursor and compares each record's unique id; Zapier dedupes on the 'id' key and lets you specify an alternate Deduplication Key when no id exists. Workato uses built-in cursor management + auto-dedup + in-order processing. Pipedream sources expose dedupe strategies (e.g. dedupe: 'unique'). Critical subtlety the UX must teach: instant/webhook triggers are generally NOT deduped by the engine — the sender must guarantee at-most-once — so the two trigger types have different guarantees. _(seen in: Zapier, Workato, Pipedream, Make)_
- **Fan-out control: split-on (one run per item) vs single batched run vs batch trigger** — When a trigger returns multiple items, the user must control whether that becomes N separate runs or one run with an array. Power Automate exposes 'split-on' (default: each item is its own run; turn off to get a single run with an array input). Workato offers single / batch / bulk trigger dispatch (batch improves throughput on large volumes; 1000-event poll cap since June 2025). Getting this wrong silently changes run counts and cost. _(seen in: Power Automate, Workato, Make)_
- **Concurrency / parallelism control on the trigger** — Lets users cap how many runs execute simultaneously (degree of parallelism) or force strictly sequential processing to avoid downstream race conditions and API rate-limit breaches. Power Automate's per-trigger Concurrency Control (off by default; set max concurrent runs) is the reference implementation. Without it, a burst of trigger events can overwhelm downstream systems. _(seen in: Power Automate, Workato, Temporal)_
- **Webhook security: secret/signature verification, IP allowlist, and a regenerate-URL action** — Any publicly reachable inbound trigger URL is an attack surface. Mature platforms support signature verification (shared secret / HMAC), let you regenerate the URL if leaked, and validate the sender. A trigger editor that hands out a raw URL with no verification guidance is a security pitfall. This is a standard expectation for production webhook triggers. _(seen in: n8n, Make, Pipedream, Power Automate)_
- **Form / chat / conversational trigger** — Increasingly common: a hosted form submission or a chat message starts the workflow. n8n's Chat Trigger fires AI/conversational workflows with the message as input; form triggers turn a workflow into a hosted intake. These broaden who can start an automation beyond developers and are now expected in AI-era editors. _(seen in: n8n, Make, Power Automate)_

**Differentiator**

- **Trigger event replay / reprocessing of past events** — When a downstream step was misconfigured, users want to re-run the workflow against trigger events that already arrived without asking the source to resend. Pipedream sources persist emitted events and expose them via REST/SSE for replay; Workato keeps a trigger event history. This turns a lost-event incident into a one-click recovery and is a strong differentiator over editors that drop events permanently. _(seen in: Pipedream, Workato, n8n)_
- **Schedule as a first-class object decoupled from the workflow (pause, backfill, overlap policy)** — Temporal Schedules are the advanced pattern: a Schedule has its own identity independent of any execution, can be paused/resumed, backfilled to replay missed intervals, and carries overlap policies (skip/buffer/allow) — far richer than a cron property baked into the workflow. This lets ops manage timing without editing the automation itself, a clear differentiator for serious orchestration use cases. _(seen in: Temporal)_
- **Durable wait-for-event mid-workflow (signal / signal-with-start)** — Beyond the initial trigger, best-in-class durable engines let a workflow PAUSE and wait for an external event arriving later, then resume — and 'signal-with-start' atomically starts the workflow if it isn't running yet, otherwise just delivers the signal. Temporal is the reference. This blurs the trigger/await boundary and enables long-running, human-in-the-loop, and rendezvous patterns that simple start-only triggers cannot express. _(seen in: Temporal)_
- **Multi-trigger workflows (multiple entry points into one graph)** — Letting several distinct triggers (e.g. a webhook AND a schedule AND a manual run) feed the same downstream logic avoids duplicating workflows. n8n supports multiple trigger nodes in one workflow (with documented caveats around certain combinations), which is a differentiator versus the strict one-trigger-per-flow model in Zapier/Power Automate. UX must make clear which trigger fired (branching on entry point). _(seen in: n8n)_
- **Hybrid instant+polling trigger (webhook primary, polling fallback to catch missed events)** — Webhooks can silently drop events (downtime, timeouts). The advanced pattern pairs an instant webhook trigger with a low-frequency polling 'reconciliation' pass that catches anything missed and dedupes against what was already processed. Make users implement this as Custom Webhook + a 2–5 min Watch module; Zapier 'Hybrid' triggers and Workato real-time-with-fallback poll do it natively. Delivers near-real-time latency with at-least-once reliability. _(seen in: Make, Zapier, Workato)_
- **Change-Data-Capture (CDC) triggers** — For database/large-system sources, CDC streams inserts/updates/deletes as ordered events rather than diffing snapshots — lower latency, guaranteed ordering, no missed intermediate states. Workato exposes CDC triggers as a distinct mechanism alongside polling/real-time/scheduled. A differentiator for data-orchestration use cases where row-level change fidelity matters. _(seen in: Workato)_
- **Throttling / rate-limit-aware trigger queueing** — When a trigger fires in bursts, an execution throttle queues runs and processes them at a controlled rate (FIFO) to stay under downstream API limits — e.g. 1000 invocations queued and run sequentially. This protects connected systems and prevents cascading failures, and is a maturity differentiator over editors that fire all runs at once and get rate-limited. _(seen in: Workato, Power Automate)_
- **Error / catch trigger that fires when another workflow fails** — A dedicated trigger type that runs only when a linked workflow errors, receiving the failure context (which workflow, which node, the error). n8n's Error Trigger builds a reusable error workflow; by default a workflow with an Error Trigger handles its own failures. This makes observability and alerting a first-class trigger pattern rather than bolted-on logging. _(seen in: n8n)_

### Workflow editor: actions and data mapping between steps (variable/field pickers, drag-to-map, expression/templating languages, formatters/transforms, type handling, test-data preview, lookups)

Across Zapier, Make, n8n, Workato, and Pipedream, the single defining move that makes data mapping usable for non-technical users is NEVER making them type a path. Every leading editor turns "reference output of an earlier step" into a point-and-click or drag-and-drop gesture against a live tree of real values, then renders the result as a labelled, removable pill (Zapier pill, Workato/Make datapill, n8n data-pill) carrying the source step icon + field name + a sample value. The path syntax ({{steps.x.field}}, {{1.field}}, $node) still exists underneath but is hidden by default; "see the syntax" is an advanced affordance, not the primary one. The second universal: the picker is only useful if it is populated with REAL data, which means the editor first runs/tests upstream steps (or pins/mocks sample data) so the picker shows actual values and a live preview of what the mapped value resolves to. The third: a clean separation between a "static value" mode and a "dynamic/expression" mode per field (n8n's Fixed|Expressions toggle, Make's map-vs-text toggle, Workato's text-vs-formula mode), so beginners stay in plain-value mode and only opt into power. Transforms/formatters are where the products diverge most: Make and n8n embed a formula/function library (date, text, number, array) directly in the mapping surface; Zapier forces transforms into explicit, discoverable "Formatter" steps (lower power, far lower confusion); Workato offers inline formula mode plus lookup tables/data tables for cross-reference enrichment. The hotelclaw codebase today (TemplateField + field-defs.ts) already implements the must-have core well — Insert-data popover, pure-ref-becomes-friendly-chip, ref pills, grouped/searchable picker with sample values, no visible braces — but is missing the populated-from-real-data picker (samples are static), drag-to-map, any transform/formatter layer, a live resolved-value preview, type-aware filtering of the picker, and lookups. The biggest non-technical-user pitfalls all cluster around invisible data types (string "26" vs number 26 silently breaking comparisons), arrays/nested data (iterate vs aggregate is the #1 conceptual wall), and empty pickers when upstream hasn't been run.

**Must-have**

- **Click/drag to insert a reference — never type the path** — The core usability unlock. Non-technical users cannot author {{steps.code.field}} or {{1.body.email}} by hand. Every leading editor makes it a gesture: Zapier '+ / type slash' opens an insert modal; Workato and n8n drag a pill from an INPUT/datatree pane and drop it onto the field, which auto-generates the expression. The user manipulates labelled fields, not syntax. _(seen in: Zapier, Make, n8n, Workato, Pipedream)_
- **Inserted reference renders as a labelled, removable pill (not raw braces)** — The mapped value shows as a chip carrying source-step icon + step number + field name (bold) + sample/preview value (gray), with an X to remove. This makes a mixed text+data field readable ('Hi {Guest name}, your {Room} is ready') and makes it obvious WHERE each value comes from. hotelclaw already does this (pure-ref -> friendly chip; mixed -> 'includes' pills). _(seen in: Zapier, Make, n8n, Workato)_
- **Searchable, grouped data picker organized by source step** — Once there are more than a few upstream steps, a flat list is unusable. Pickers group fields under their producing step (trigger first, then each step in order) and offer a search box that matches label/path/group. hotelclaw's InsertDataPopover already groups via groupRefs + search; this is table stakes. _(seen in: Zapier, Make, n8n, Workato, Pipedream)_

**Standard**

- **Picker shows a real sample value next to each field** — Users pick the right field by recognizing its value ('e.g. room 203', 'e.g. jane@...'), not by guessing from a name. This is why editors run/test upstream steps first. hotelclaw shows r.sample, but those samples are static; the differentiator is sampling from an ACTUAL recent run. _(seen in: Zapier, Make, n8n, Workato)_
- **Populate the picker from a real test run, with pin/mock of sample data** — The picker is only as good as the data behind it. n8n runs upstream nodes and lets you PIN data so tests are consistent and edge cases reproducible; Make requires running the scenario once to materialize mappable fields (and notably FAILS when optional keys were absent from the last sample — a known pitfall); Zapier pulls a sample record. Without this, fields the user needs simply don't appear. _(seen in: Make, n8n, Zapier, Workato)_
- **Live resolved-value preview of the field as-configured** — Below an expression/field, the editor shows what it evaluates to RIGHT NOW given sample data, so users see 'Hi Jane, your room 203 is ready' before running. This collapses the edit-run-inspect loop and catches undefined/empty refs immediately. n8n's expression editor and Make's mapping panel both preview the resolved output. _(seen in: n8n, Make, Pipedream)_
- **Per-field Static vs Dynamic mode toggle** — Keeps beginners in plain-value mode and hides expression machinery until opted into. n8n's hover 'Fixed | Expressions' toggle, Make's map/unmap (text vs mapped) toggle, Workato's text-vs-formula mode. hotelclaw blends these (a field is bound-chip when it's a pure ref, else free text) which is elegant but loses the explicit affordance that there IS a dynamic mode. _(seen in: n8n, Make, Workato)_
- **Type-aware fields and picker filtering** — Each parameter has an expected type (text/number/date/boolean/list); the picker ideally surfaces or prioritizes type-compatible refs and labels each ref's type in plain language. hotelclaw has FRIENDLY_TYPE (Text/Number/Yes-no/List/Data) and RefType, but does not yet filter the picker by the target field's type — a clear next step. _(seen in: Make, n8n, Workato, Zapier)_

**Differentiator**

- **Formatters / transform functions for date, text, number, array** — The most-requested real-world need: reformat a date, uppercase/trim text, parse a number, join/split a list. Two design schools: (a) inline function library in the mapping surface (Make's General/Math/Text/Date/Array tabs; n8n expression functions) — powerful but intimidating; (b) explicit transform STEPS (Zapier Formatter with Format Number / Format Date / Format Phone) — discoverable, beginner-safe, but adds nodes. Workato offers inline formula mode. hotelclaw has NEITHER yet; this is the single biggest gap vs the field. _(seen in: Make, n8n, Zapier, Workato)_
- **AI-assisted mapping / formatter suggestion in plain language** — 2025-2026 frontier: describe the transform in words ('format this as MM/DD/YYYY') and the tool drafts the Formatter step or expression; Zapier Copilot also auto-suggests/auto-populates mapped field values. Lowers the expression-language wall entirely for non-technical users. _(seen in: Zapier, Workato)_
- **Lookup tables / data tables for cross-reference enrichment** — Maps a key to a value without branching logic (status code -> label, region -> manager email). Workato lookup tables and data_table_lookup() formula fetch records inline; this is how non-technical users do enrichment without code. Relevant to hotelclaw's action.entity.find, which is a lookup primitive but not surfaced as an inline mapping affordance. _(seen in: Workato, Make)_
- **Explicit array iterate vs aggregate model with per-item mapping** — Lists are the conceptual cliff for non-technical users. Make makes it a first-class pattern: Iterator splits an array into bundles, downstream maps a single item, Aggregator recombines. n8n's items model and Loop Over Items / Loop Output define what is collected after the loop. hotelclaw has control.foreach with an item_var name, but the mapping UX for 'the current item's field' inside the loop is the hard part to get right. _(seen in: Make, n8n, Workato)_
- **Custom/manual pill mapping for fields absent from the sample** — Escape hatch for when a field exists in real data but not in the captured sample (very common with optional keys). Zapier supports custom pill mapping; without it users hit a wall. Pairs with the 'empty picker' pitfall. _(seen in: Zapier)_
- **Schema preview without running (expected fields before first execution)** — n8n Schema Preview exposes a previous node's expected output schema so you can drag fields in before providing credentials or executing — removes the chicken-and-egg of 'run to see fields, but configure before running'. A meaningful polish for first-time setup. _(seen in: n8n)_
- **Auto-map by matching field names (bulk mapping)** — Workato group data mapping auto-maps when source datapill name matches the destination field name, a big time-saver when mapping many fields at once (e.g. record -> record copy). _(seen in: Workato)_

### Control flow in workflow editors (branching, filters, loops, delays, wait-for-event, sub-workflows, parallelism, error handling)

Control flow is what separates a linear "trigger → action" automation from a real workflow engine. Across the 2025-2026 incumbents, control flow has converged on a fairly stable vocabulary: a binary filter/gate (continue-only-if), an N-way branch/router with AND/OR rule groups and a fallback/else lane, loops over lists with batching, durable delays, wait-for-external-event (webhook/form/human approval), reusable sub-workflows, and error/catch lanes. The differentiators in 2025-2026 are durability (state survives restarts and multi-day waits — Temporal's model, now imitated by n8n's DB-offloaded Wait), true parallel fan-out/fan-in with a join that waits for all branches, and first-class human-in-the-loop approval steps (Zapier and n8n both shipped dedicated HITL primitives). The two biggest UX battlegrounds are (1) how branch routing semantics are communicated — exclusive (first-match-wins, Make routers / Switch) vs. non-exclusive (every matching branch runs, classic Zapier Paths) — because getting this wrong silently runs the wrong branches; and (2) how branches that split are rejoined, since most engines do NOT auto-rejoin and require an explicit merge/join node, which is a notorious source of user confusion (duplicate runs, lost items, merge waiting forever). For a builder UI, the must-haves are filter gates, multi-branch routing with a visible fallback/else lane, clear per-branch condition summaries, and at least basic loop + delay; standard tier adds wait-for-event, error branches, and sub-workflows; differentiators are durable long-waits, parallel fan-out/fan-in with join, native approval steps, and per-step retry policies.

**Must-have**

- **Filter / continue-only-if gate (single-path guard)** — The simplest and most-used control primitive: halt the run unless a condition is met. It is conceptually distinct from branching — there is one path, and the run either proceeds or stops silently. Users reach for it constantly (e.g. 'only continue if status = booked'). UX pattern: a dedicated Filter step rendered inline in the path with a one-line human-readable summary ('Only continue if Amount > 100'); when it stops, the run is marked 'filtered/did not continue' rather than 'failed' — distinguishing a deliberate stop from an error is critical so users don't chase phantom failures. _(seen in: Zapier, Make, n8n, Workato)_
- **Multi-branch router / paths / switch (N-way conditional split)** — The core branching primitive: route the run to one of several lanes based on conditions. UX patterns differ by product and the differences are load-bearing. Zapier Paths renders each branch as a parallel vertical lane with its own rule set; Make's Router fans modules out into visually diverging routes; n8n's Switch node exposes labeled outputs (one connector per case) plus a fallback output. Each branch needs an editable name/label, a rule group, and a visible position because order can determine evaluation. The router is what makes a workflow feel like a flowchart rather than a script. _(seen in: Zapier, Make, n8n, Workato, Temporal)_
- **AND/OR condition groups within a branch rule** — A branch or filter rarely tests one field. Users need 'match ALL of these' (AND) vs 'match ANY of these' (OR), and increasingly nested groups (AND of ORs). Zapier exposes explicit And/Or logic per path branch; Make filters chain operators; n8n's IF/Filter v2 has a visual condition builder with combinator toggles and typed operators (string/number/date/boolean, exists/empty). UX pattern: a condition-builder with rows of [field][operator][value], a group-level AND/OR toggle, and live type-aware operator lists. Getting operator semantics right (case sensitivity, type coercion, empty vs null) is where most user bugs originate. _(seen in: Zapier, Make, n8n, Workato)_
- **Fallback / else / default branch** — Every router needs a 'none of the above' lane, or data silently falls through and nothing runs. Zapier lets you mark exactly one branch per group as the fallback ('runs if no other branch's rules are met'); n8n's Switch has a dedicated fallback output; Make uses an unfiltered route as the catch-all. UX pattern: an explicitly labeled, visually distinct default lane that cannot have conditions, plus validation that warns when no fallback exists (so unmatched runs aren't dropped invisibly). _(seen in: Zapier, n8n, Make)_
- **Loop / iterate over a list (foreach) with batch size** — Workflows constantly receive arrays (line items, search results, rows) and must act per element. n8n's Loop Over Items splits items into batches (Batch Size = 1 for true per-item), loops the connected branch, then emits a 'done' output; Make pairs an Iterator (array → individual bundles) with downstream per-bundle processing; Workato has Repeat-for-each and Repeat-in-batches. UX patterns: a loop node with a configurable batch size, a body sub-region, a loop-back connector, and a separate 'done/after-loop' output. Pitfall surfaced repeatedly: silent caps (a reported n8n bug where a loop stopped at 10 iterations) and confusing per-item vs per-batch data context. _(seen in: n8n, Make, Workato)_

**Standard**

- **Aggregator / collect loop results back into one array (loop fan-in)** — The inverse of iteration: after processing items individually, recombine them into a single payload for downstream steps. Make's Array Aggregator scoops multiple bundles back into one array and supports 'Group By' to bucket by a field; n8n uses a Merge/aggregate or the loop's done output. Without this, users get one downstream run per item when they wanted one consolidated run. UX pattern: an aggregator step that pairs visually with its source iterator/loop and lets you pick which fields to collect and an optional grouping key. _(seen in: Make, n8n, Workato)_
- **Delay / wait-for-duration / wait-until-timestamp** — Pausing for a fixed interval or until a specific time is foundational for drip sequences, SLA gaps, and rate limiting. n8n's Wait node offers 'After Time Interval' and 'At Specified Time' and offloads state to the DB so the workflow resumes exactly where it left off; Zapier has Delay; Temporal exposes durable timers that 'sleep for months' surviving worker downtime. UX pattern: a delay step with mode toggle (duration vs absolute time vs dynamic expression) and a clear indication in run history that the run is 'waiting until <time>' rather than stuck. _(seen in: Zapier, n8n, Make, Temporal)_
- **Wait-for-external-event (webhook / form / resume URL)** — Long-running workflows must pause until something external happens — a callback, a form submission, an inbound webhook. n8n's Wait node can resume on an incoming call to $execution.resumeUrl or on form submit; Temporal models this as Signals (ordered, fire-and-forget external messages that mutate a running workflow). This is what turns automation into orchestration. UX pattern: a wait node that surfaces a generated resume/callback URL, optionally a timeout-after-N with a separate 'timed out' output path, and run-history state showing 'waiting for event'. _(seen in: n8n, Temporal, Zapier)_
- **Sub-workflows / callable reusable modules** — Factoring shared logic into a reusable unit called from many workflows is essential for maintainability at scale. n8n's Execute Workflow node calls a sub-workflow (sync or async, once or per-item); Workato's Call Recipe Function invokes a recipe function synchronously (caller waits) or asynchronously (fire-and-forget); Temporal's Child Workflows can run on entirely separate workers as their own service and partition event history. UX pattern: a 'call workflow/function' node with input mapping, a sync/async toggle, and output mapping back; plus the ability to define a workflow's input contract. Pitfall: error propagation from sub-workflows (n8n's Execute Workflow node has documented quirks where retries/continue-on-error still surface as errors). _(seen in: n8n, Workato, Temporal)_
- **Merge / join node to recombine branches** — Independent of parallelism, any time a flow splits (router, IF, loop) and needs to converge, you need an explicit merge. n8n's Merge node combines branches by append, by matching field values (enrich/join), or by position, and waits for required inputs. This is repeatedly cited as a top source of confusion — merge returning wrong/filtered data, or waiting forever for an input that a branch never produced. UX pattern: a merge node with selectable mode (append / combine-by-key / by-position / choose-branch), clear indication of which inputs are required, and guidance so a never-firing input doesn't deadlock the run. _(seen in: n8n)_
- **Error / catch branch (try-catch block around steps)** — Production workflows must define what happens on failure at the step or block level. Make attaches an error route (a parallel path that activates only when a module fails, added via right-click) with directives ignore/resume/commit/rollback/break; Workato's 'Handle errors' control statement monitors a block and runs corrective steps (retry, log, alert, alternate path); n8n offers a per-node 'error output' (continue-using-error-output) plus a workflow-level Error Trigger. UX pattern: the ability to attach an on-error lane to a step or wrap a group in a monitored block, with the error object (message, code, failed item) available to downstream steps in that lane. _(seen in: Make, Workato, n8n, Temporal)_
- **Per-step retry policy (attempts, interval/backoff)** — Transient failures (timeouts, rate limits) should auto-retry before falling to an error branch. Make's Break directive sends failed runs to an Incomplete Executions queue and exposes retry attempt limit (1-10) + interval-between-retries; n8n has node-level 'Retry On Fail' with attempts and wait-between-tries; Temporal has rich activity retry policies (backoff, max attempts) as a core feature. UX pattern: per-step settings for max attempts, delay between attempts, and optional backoff, plus a clear distinction between 'retried then succeeded' vs 'exhausted retries → error path'. Pitfall: interaction between retry and continue-on-error is subtle (a known n8n issue where Retry-On-Fail misbehaves when On-Error=Continue). _(seen in: Make, n8n, Temporal)_
- **Nested / grouped branching (paths within paths, blocks)** — Real logic needs hierarchy: a branch that itself branches, or a monitored/loop block containing many steps. Zapier supports nesting Path groups up to three levels deep (a documented workaround for its 10-branches-per-group cap); Workato nests conditional/repeat/error blocks; n8n nests via sub-workflows and chained IF/Switch. UX pattern: collapsible block containers with clear visual nesting/indentation, and per-block scope for variables and error handling. Pitfall: deep nesting becomes unreadable fast, so good editors add collapse, a tree/outline view, and per-branch summaries. _(seen in: Zapier, Workato, n8n)_
- **Human-readable per-branch condition summaries on the canvas** — Not a flow primitive but a critical UX feature: each branch/filter should show its rule in plain language on the node ('If priority is High AND assignee is set') without opening the inspector. This is how users scan a complex flowchart and trust it. All mature editors surface some inline summary; the quality of this summary (typed values, AND/OR rendering, truncation with tooltip) heavily affects perceived polish and reduces misconfiguration. _(seen in: Zapier, Make, n8n)_

**Differentiator**

- **Branch evaluation semantics: exclusive (first-match) vs non-exclusive (all-match)** — This is the single most error-prone concept in branching and a key UX-communication problem, not just a feature. Make routers and n8n Switch are effectively exclusive/explicit-output (data goes down a chosen route). Classic Zapier Paths are NON-exclusive: 'Zapier continues evaluating all path branches beyond the first matching one, and if multiple paths' conditions are met, ALL of those paths' actions run' — and Zapier even changed execution (parallel vs sequential) at a June 2025 cutoff. A good builder must make this explicit in the UI ('first matching branch only' vs 'every matching branch') because the wrong assumption silently runs duplicate work. _(seen in: Zapier, Make, n8n)_
- **Human-in-the-loop / approval step with timeout and escalation** — A first-class, productized form of wait-for-event: pause for a person to approve/reject before continuing. Both Zapier (dedicated 'Human in the Loop' / Request Approval with timeout settings, auto-continue-or-stop on no response, and reminder follow-ups) and n8n (HITL via Wait + Slack/email approve buttons) shipped this as a named pattern in 2025. Temporal's 'human approval' is one of its canonical patterns. UX pattern: an approval node configuring approver(s), channel (email/Slack), approve/reject branches, a timeout, and a default outcome on timeout (continue / stop / escalate to backup owner). _(seen in: Zapier, n8n, Temporal, Workato)_
- **Parallel branches with fan-out and fan-in (join that waits for all)** — Running independent branches concurrently to cut latency, then joining when all complete. Temporal makes this native (concurrent activities/child workflows, await-all). n8n approximates it with parallel async sub-workflow execution plus a Wait/Merge fan-in that pauses until all callbacks return. The hard part is the JOIN: most engines do NOT auto-rejoin split branches — n8n requires an explicit Merge node, and a Merge with two inputs waits for both before firing. UX pattern: a parallel/split node, visibly concurrent lanes, and an explicit join/merge node with a documented wait policy (wait-for-all vs first-to-finish vs merge-by-key). This is a strong differentiator because few no-code tools do true parallelism well. _(seen in: Temporal, n8n)_
- **Durable / resumable state across restarts and multi-day waits** — The deepest differentiator. Temporal's whole value proposition is durable execution — workflows survive worker/platform crashes, sleep for months, and replay deterministically from event history (Continue-As-New to bound history). n8n's v2 Wait node offloads state to the database so a paused workflow resumes with the same data even after a restart. For long-running, scheduled, or human-gated control flow, durability is what makes delays and waits trustworthy rather than fragile. UX implication: run history must represent paused/sleeping/waiting states as first-class, and resuming must restore full context. _(seen in: Temporal, n8n)_

### Testing, Debugging, Error Handling & Observability in Workflow Tools

Across Zapier, Make, n8n, Workato, and Temporal, debuggability splits into two cultures. The no-code crowd (Zapier, Make, n8n, Workato) optimizes for a non-technical operator who needs to answer "did it run, which step broke, what data went through it, and can I re-fire it without making a mess." The durable-execution crowd (Temporal) optimizes for engineers who need a replayable, deterministic event history as the source of truth. The modern (2025-26) bar blends both: every product now offers per-step inputs/outputs in run history, node/step-level retry with exponential backoff, a dedicated error-handler path, centralized failure monitoring, and — newest of all — AI-generated plain-English error explanations (Zapier shipped this; Make added an enhanced error dashboard).

For NON-TECHNICAL users specifically, what makes a failure debuggable is: (1) the run history shows a visual flow with the failing step highlighted and a red/green status per step, not a log dump; (2) clicking a step reveals the exact data in and data out, so the user can see "the phone field was empty" rather than read a stack trace; (3) the error message is translated to plain English with a likely cause and concrete next step; (4) re-running is a one-click "replay" that re-uses the captured input data, so they don't have to recreate the trigger; and (5) idempotency/duplicate risk is surfaced or handled, because a naive replay is the #1 way non-technical users create duplicate records. The biggest cross-product pitfall is that "replay" almost always restarts from the trigger, not from the failed step (only Temporal truly resumes mid-flow), which silently re-runs already-successful side effects.

KEY UX PATTERNS TO STEAL: pin/mock sample data so a step can be tested in isolation without re-hitting live APIs (n8n's data pinning); "Test step" that runs just the selected node plus only the upstream nodes needed to feed it; a per-step status vocabulary richer than pass/fail (Zapier's "Stopped/Handled" for steps an error-handler caught, "Success" for the handler path itself); an Incomplete Executions queue (Make) that is a true dead-letter queue where each entry stores the error, the bundle data, and the remaining flow, and is editable before retry; declarative retry policy with backoff + a list of non-retriable error types so you don't loop on poison messages (Temporal, n8n); and a global/workspace-level error trigger (n8n Error Trigger, Workato RecipeOps Job-failed) that catches anything uncaught and routes it to Slack/email with a deep link straight to the failed run.

**Must-have**

- **Test/run a single step in isolation ('Test step' / 'Execute node')** — Lets a builder validate one step's config without re-running the whole workflow. The crucial UX detail: it runs the selected step PLUS only the minimum upstream steps needed to supply its input, then shows that step's raw output inline. Non-technical users learn the workflow by clicking each step and watching real data appear. _(seen in: n8n, Zapier, Make, Workato)_
- **Step-by-step execution view with per-step pass/fail status and the failing step highlighted** — The single most important debuggability primitive for non-technical users: a visual rendering of the run where each step is green (ran), red (failed), or grey (skipped), so you can see WHERE it broke at a glance instead of parsing logs. Make highlights the erroring module on the canvas; Zapier shows a per-step run detail timeline. _(seen in: Make, Zapier, n8n, Workato, Temporal)_
- **Run history with inputs AND outputs captured per step** — Being able to click any past run and inspect the exact data that entered and exited each step is what turns 'it failed' into 'the address field was blank.' Non-technical users debug by reading data, not code. This is table stakes now and the foundation every other debugging feature builds on. Temporal's Event History is the strongest form — a complete, queryable, replayable audit trail. _(seen in: Zapier, Make, n8n, Workato, Temporal)_
- **Per-step retry policy with exponential backoff** — Transient failures (timeouts, 429 rate limits, network blips) should self-heal without human involvement. The mature pattern is configurable max attempts + delay + exponential backoff (n8n: 3 retries, 2s delay, backoff toggle; Zapier autoreplay: 5 attempts on a 5m/30m/1h/3h/6h schedule; Workato: up to 3 retries, 1-10s interval, plus a 'Retry IF' condition). Defaults should be sane so non-technical users get resilience for free. _(seen in: Temporal, n8n, Zapier, Workato)_
- **Dedicated error-handler / fallback path per step** — When a step fails you want an alternate branch (log it, notify, substitute a default, route to a human) rather than killing the run. Zapier's per-step Error Handler runs as an alternate path and marks the original step 'Stopped/Handled'; Make attaches error routes per module with directives; Workato's 'Handle errors' block monitors a group of steps and runs a recovery block. The richer status vocabulary (handled vs failed vs skipped) is itself a key UX signal. _(seen in: Zapier, Make, Workato, n8n)_
- **Replay / re-run a failed run (one-click, reuses captured trigger data)** — A non-technical user can't always recreate the original trigger event (the webhook already fired, the email already arrived). Replay re-runs using the stored input data from history, so recovery is one click. Zapier's manual Replay and Autoreplay, Make's incomplete-execution retry, and Temporal's reset all serve this. The key UX win is not making the user reproduce the trigger. _(seen in: Zapier, Make, Temporal, n8n)_
- **Failure alerts via Slack / email with deep link to the failed run** — Silent failures are the worst outcome. A good alert names the workflow, the run/execution ID, the error message, and — critically — a deep link that opens the exact failed execution. n8n error workflows post to Slack instantly; Zapier emails after autoreplay exhausts. The deep link is what makes the alert actionable instead of just anxiety-inducing. _(seen in: n8n, Zapier, Make, Workato)_

**Standard**

- **Run with sample / pinned / mocked data** — n8n's data pinning saves a node's output and reuses it on subsequent test runs instead of re-fetching, which avoids burning live API quota, hitting rate limits, or mutating real records while iterating. Critical for testing destructive steps (send email, create invoice) safely. Without it, every test edit re-calls paid/side-effecting APIs. _(seen in: n8n, Zapier, Make)_
- **Dead-letter queue for failed runs (Make 'Incomplete Executions')** — Failed runs land in a queue that stores the error, the input/bundle data, and the remaining flow, so nothing is lost. The operator can inspect, EDIT the bundle data before retrying (e.g. fix the bad phone number), retry one or many at once, or delete. This 'fix-then-retry' loop is the most non-technical-friendly recovery model because the user corrects data in place rather than re-triggering the source. _(seen in: Make, Workato)_
- **Idempotency / duplicate-prevention support for safe retries** — Because most products replay from the trigger, a naive retry duplicates records (creates the lead twice, charges the card twice). Mature setups need external-ID/upsert/dedup-key patterns, often via a Data Store keyed on OrderID+Action checked before irreversible actions. The #1 footgun for non-technical users; the best products surface or automate this rather than leaving it to the builder. _(seen in: Make, Temporal, Workato)_
- **Global / workspace-level error trigger catching anything uncaught** — Per-step handlers miss novel failures; a catch-all safety net routes any uncaught error to centralized logging/alerting. n8n's Error Trigger (set per-workflow under Settings > Error Workflow) receives execution ID, error message, stack trace, and last node; Workato's RecipeOps 'Job failed' trigger fires workspace-wide with error type/message/app/action/step. The recommended pattern is three layers: node retries, global error trigger, centralized logging. _(seen in: n8n, Workato)_
- **Centralized failure monitoring dashboard with trends and error rates** — Beyond single-run debugging, operators need to see recurring failures and error-rate spikes across all workflows in one place. Make shipped an Enhanced Error Monitoring Dashboard (2026) with trend analysis; Workato's RecipeOps centralizes cross-recipe failure tracking; n8n exposes metrics for Grafana. Turns reactive firefighting into proactive detection. _(seen in: Make, Workato, n8n, Temporal)_
- **Debug/trace mode showing raw HTTP requests & responses per step** — For the harder class of failures, a deeper trace exposes the actual headers, payload, and response body of each external call. Workato's job debug tracing surfaces full HTTP request/response per action. This is the escalation path when the friendly inputs/outputs view isn't enough — aimed at power users/admins, not first-line operators. _(seen in: Workato, n8n)_
- **Configurable retry-exhaustion behavior (halt, park, or alert after final attempt)** — What happens after retries fail must be explicit and visible. Zapier suppresses error emails during the autoreplay window then sends ONE email after the final attempt (~10h later); during that window manual replay is blocked. Builders need to understand and control this so failures aren't buried for hours. Make auto-retries only specific transient error types (rate-limit, connection, timeout). _(seen in: Zapier, Make)_

**Differentiator**

- **Non-retriable error classification (avoid poison-message loops)** — Retrying a 400 'invalid email' forever wastes runs and delays the failure alert. Temporal lets you mark specific exceptions/HTTP statuses as non-retriable so permanent errors fail fast while transient ones retry. Distinguishing transient vs permanent errors is what separates a smart retry engine from a dumb loop. _(seen in: Temporal, n8n)_
- **Error-handling directives: Ignore / Resume / Commit / Rollback / Break (transactional semantics)** — Make's five directives let a builder choose what 'recover' means: Resume substitutes a value and continues; Commit keeps partial successes; Rollback attempts to revert transaction-aware modules; Break parks the run in the dead-letter queue. This gives fine-grained control over partial-failure consistency — though the honest caveat (a pitfall) is Rollback can't un-send already-fired API calls. _(seen in: Make, Temporal)_
- **Resume from the exact point of failure (not restart from trigger)** — True differentiator and the cleanest answer to the duplicate-side-effect problem. Temporal replays event history and SKIPS already-completed activities — only the failed step onward re-runs, so successful side effects aren't repeated. By contrast Make/Zapier replay restarts from the beginning, which re-fires earlier steps. Mid-flow resume is rare and valuable. _(seen in: Temporal)_
- **AI plain-English error explanation with likely cause + suggested fix** — The newest 2025-26 leap for non-technical debuggability. Zapier's AI troubleshooting turns a raw error into: a summary of what went wrong in plain language, which step caused it, the likely cause, and concrete next steps — shown alongside the original error and the step's inputs/outputs. This is the single feature most directly aimed at users who can't read stack traces. _(seen in: Zapier, Make)_
- **OpenTelemetry / metrics export for external observability stacks** — Production teams want workflow telemetry (node-level timing, error spans, traces) in their existing Grafana/SigNoz/Prometheus stack rather than a walled-garden dashboard. n8n exports via OpenTelemetry; Temporal emits rich metrics and is observability-first by design. A differentiator for engineering-led deployments, not for non-technical users. _(seen in: n8n, Temporal)_

### Workflow editor authoring experience (onboarding, AI generation, editing ergonomics, collaboration, versioning, lifecycle)

The single biggest lever on "time-to-first-working-automation" in 2025-2026 workflow editors is collapsing the blank-canvas problem. The market has decisively moved away from "drag nodes for an hour" toward two complementary on-ramps: (1) a Describe -> Monitor -> Refine natural-language loop where the user types intent in plain English and the AI emits a complete, pre-wired, pre-configured graph (n8n AI Workflow Builder, Oct 2025; Zapier Copilot; Lindy Agent Builder "vibe-code in 30 seconds"; Gumloop AI builder); and (2) a rich template/clone path where galleries seed a working draft that the user customizes rather than authors from scratch. The decisive UX detail in the AI path is multi-turn conversational refinement that mutates the live canvas in place (not a one-shot generate), because real first workflows are never right on the first prompt. The second lever is editing ergonomics that match desktop-software muscle memory: undo/redo, copy/paste/duplicate of steps (including cross-workflow paste), a Cmd+K command palette, and keyboard-driven canvas navigation. The third, which separates toy builders from team/production tools, is lifecycle and safety: explicit draft-vs-published states with the state badged next to the title, full version history with restore/rollback, and visual change diffs (n8n's color-coded added/removed/modified/renamed node graph) so editors can see exactly what changed before publishing. Collaboration (real-time co-editing, threaded comments, sticky-note annotations) is emerging but still uneven across the majors and reads as a differentiator. The recurring pitfalls are: a one-shot AI generation with no in-place refinement, missing or shallow undo, copy/paste that doesn't carry configuration/credentials, "save = deploy" with no draft buffer, and no diff/rollback so users fear editing a live automation. For HotelClaw's builder, the highest-ROI investments are: AI NL-to-workflow with conversational refinement, a strong empty state that routes to templates AND the AI prompt box, robust undo/duplicate/copy-paste, draft-vs-published with a clear badge, and version history with restore.

**Must-have**

- **Empty-state that routes to BOTH a template gallery and an AI prompt box (not a blank canvas)** — The blank canvas is the #1 cause of abandonment before first success. A first-run state that offers (a) curated/popular templates by category and (b) a 'describe what you want to automate' input lets the user reach a working draft in seconds instead of learning node mechanics first. This directly compresses time-to-first-working-automation. _(seen in: Zapier, n8n, Make, Lindy, Gumloop)_
- **Template gallery with one-click clone-to-edit (original stays untouched)** — Templates let users start from a known-good working graph and modify fields/statuses/integrations rather than author from zero. The key UX nuance is 'clone creates your own editable copy; the source template is immutable,' plus per-template setup tutorials/checklists that walk through required credentials and field mapping so the cloned flow actually runs. _(seen in: Gumloop, Make, Zapier, Lindy, n8n)_
- **Natural-language workflow generation (prompt -> complete pre-wired graph)** — Describing 'When X happens, do Y then Z' in plain English and getting a complete workflow with configured nodes, connections, and data flow is the largest single reduction in authoring time. Lindy markets a full agent 'in 30 seconds from a prompt'; n8n shipped the AI Workflow Builder (beta) Oct 2025; Zapier Copilot builds Zaps, tables, forms and chatbots from one chat. This is rapidly becoming table stakes, not a differentiator. _(seen in: Zapier, n8n, Lindy, Gumloop)_
- **Multi-turn conversational refinement that mutates the live canvas in place** — The make-or-break detail of the AI path. First prompts are never right; users must be able to keep chatting ('add a Slack step', 'branch on priority', 'change the field mapping') and watch the AI update the SAME workflow live, rather than regenerating from scratch. n8n explicitly frames this as the Describe -> Monitor -> Refine loop. Without in-place refinement, NL generation is a demo, not a tool. _(seen in: n8n, Zapier, Lindy)_
- **Undo / redo on the canvas (Cmd+Z / Cmd+Shift+Z)** — Editors expect desktop-grade reversibility. Without undo, every experiment is risky and users slow down or avoid editing. n8n binds Ctrl+Z / Ctrl+Shift+Z. This must cover node add/delete/move, connection changes, and config edits, and ideally AI-applied changes too so a bad AI refinement is one keystroke to revert. _(seen in: n8n, Make, Power Automate, Zapier)_
- **Copy / paste / duplicate steps, including paste across workflows** — Reusing a configured step is faster than rebuilding it. The high-value version carries the node's full configuration (and ideally credential references) on paste, and supports pasting into a DIFFERENT workflow (n8n copies via Cmd+C/Cmd+V and can paste whole workflows). Plain duplicate-in-place handles the common 'one more branch like this' case. Note n8n historically had gaps/bugs here (community issue 13636), which is exactly the pitfall to avoid. _(seen in: n8n, Make, Gumloop)_
- **Draft vs Published states with the state badged next to the workflow title** — Separating the editing buffer from the live automation lets users save partial/in-error work without affecting production. Power Automate (GA'd to all regions Feb 2025) saves drafts even WITH errors and shows a Draft/Published badge beside the title. 'Save = deploy' is dangerous and discourages iteration on live flows; an explicit publish step is a safety gate. _(seen in: Power Automate, Make, n8n)_
- **Enable / disable (activate / deactivate) a workflow without deleting it** — Operators need to pause an automation (debugging, seasonal, incident) and turn it back on with one toggle. A simple active/inactive switch is a basic operational primitive and the safest rollback lever when something misbehaves in production. _(seen in: n8n, Make, Zapier, Power Automate)_
- **Naming, descriptions, folders/tags for organizing workflows** — Once a team has more than a handful of automations, findability dominates. Named flows, descriptions, folders/tags, and search prevent the 'which Zap was that?' problem. Low glamour but mandatory for any multi-workflow account. _(seen in: Zapier, Make, n8n, Power Automate, Gumloop)_
- **Test / execute-and-refine from inside the editor with live data preview** — Seeing real data flow through each step while authoring is how users confirm the automation actually works before publishing. n8n's 'Execute and refine' runs the flow and feeds results back into the AI loop; per-node test data preview lets users map fields against real payloads. Without this, 'working' is a guess until production. _(seen in: n8n, Zapier, Make)_

**Standard**

- **Version history with restore / rollback to a prior version** — The safety net that makes editing live automations psychologically safe. n8n stores previous versions with a canvas preview and lets you open versions in new tabs to compare; Power Automate co-owners see full version history (stored in Dataverse) of who changed what; Make supports scenario history and restore/recover. One-click 'restore this version' turns a bad change from a crisis into an undo. _(seen in: n8n, Power Automate, Make)_
- **Cmd+K command palette for adding nodes and running actions** — Power users author far faster by keyboard than by mouse-hunting a node panel. n8n exposes a command bar via Ctrl/Cmd+K (or the canvas magnifier) to add nodes and trigger actions. It also doubles as in-context discovery of available steps/integrations, lowering the learning curve. _(seen in: n8n)_
- **Full keyboard shortcut set for canvas navigation (zoom-to-fit, pan, select-all, zoom)** — Navigating large graphs is painful without shortcuts. n8n provides zoom in/out (+/-), reset (0), zoom-to-fit (1), space+drag or ctrl+drag to pan, Ctrl+A select-all. 'Zoom to fit' in particular is the orientation primitive for any non-trivial workflow. Signals a builder designed for real, large workflows rather than toy demos. _(seen in: n8n)_
- **Inline validation / error surfacing while editing (not only at run time)** — Showing missing required fields, unmapped data, and broken connections as you build (rather than failing on first execution) shortens the edit-test loop. Power Automate notably still requires publishing a runnable flow before testing, which is the friction to beat. Catching errors in the draft keeps users in flow. _(seen in: n8n, Zapier)_
- **Example / starter prompts in the AI builder** — A blank prompt box is its own blank-canvas problem. Offering pickable example prompts ('Monitor competitor pricing and send weekly updates') teaches users what the AI can do and gives a one-click path into the Describe->Refine loop. Small touch, meaningful effect on activation. _(seen in: n8n, Lindy)_

**Differentiator**

- **Visual change diff between versions (added / removed / modified / renamed nodes)** — Before publishing or pulling a change, editors need to see EXACTLY what changed. n8n's Workflow Diff renders a color-coded graph (green added, red removed, yellow modified, blue renamed) and stacks remote vs local versions; community tools generate diff reports. This is what makes reviewing someone else's change (or your own AI-generated change) trustworthy. Still rare enough to read as a differentiator. _(seen in: n8n)_
- **Real-time multiplayer co-editing of a workflow** — Multiple teammates editing the same flow simultaneously (with presence) removes the serialize-and-handoff bottleneck for ops teams. Relay.app markets 'multiplayer automation'; it remains uneven across the majors, so it differentiates a builder positioned for teams rather than solo authors. _(seen in: Relay.app)_
- **Threaded comments / annotations and sticky notes on the canvas** — Asynchronous review needs in-context discussion: tag a teammate on a specific step, reply in a thread, resolve. n8n supports Shift+S sticky notes for inline documentation; richer threaded commenting (tag, reply, resolve) is common in adjacent design/collaboration tools but not yet standard in workflow builders, making it a differentiator for review-heavy teams. _(seen in: n8n, Miro (adjacent pattern))_

### Workflow builder — Canvas & flow rendering / interaction

The builder ships TWO completely separate canvas implementations for the same spec, toggled by the "Steps"/"Map" view tabs in builder-shell.tsx. The "Steps" (Flow) view is a hand-rolled vertical Zapier-style rail: TreeList renders a recursive Rail/BranchLanes tree of cards inside a custom transform-based PanZoomCanvas, with dnd-kit drag-reordering, a numbered-ordinal rail, branch lanes (Then/Else/Otherwise), inline insert "+" rows, an End/empty-lane terminus, and a full-screen searchable PaletteDialog with keyboard nav. The "Map" view is a @xyflow/react graph (WorkflowCanvas) with free-form node positions, draggable nodes, hand-dragged edge connections, per-handle branch/error outputs, a MiniMap, auto-layout, and a left palette with drag-to-canvas. The two surfaces share only the underlying spec and the catalog; they have divergent and in places incorrect mutation logic (insert, delete, branch support), two unrelated pan/zoom systems with different zoom limits, and no shared affordances (no undo, multi-select, or copy/paste in either). The Flow view is the more correct and polished of the two; the Map view's add/delete paths are buggy enough to corrupt or disconnect a workflow.

### Node inspector & per-step config editing

The node inspector is a non-modal right-side panel that swaps between a TriggerEditor and a StepEditor based on the selected node, autosaving every keystroke into the in-memory spec (node-inspector.tsx:114-149, :424-438). Each editor is composed as a numbered vertical "flow rail" (inspector-flow-layout.tsx, step-editor-flow-layout.tsx, trigger-editor-layouts.tsx) whose slots are filled with a friendly typed form, a condition/branch builder, a schedule builder, a data-context recap, and a collapsed Advanced section. The typed form is data-driven from STEP_FIELDS (field-defs.ts) via TypedStepForm, which dispatches eight field kinds (template/text/textarea/enum/number/duration/string-list/key-value/channel) to bespoke renderers (typed-step-form.tsx:137-214). Templating is hidden behind an "Insert data" picker that stores {{dotted.path}} but presents it as friendly chips (template-field.tsx). The design is strongly oriented toward non-technical users — plain-English summaries, inline-editable step names, snake_case ids demoted to Advanced — but the architecture leans entirely on the per-step-type STEP_FIELDS map, so config quality degrades to a raw-JSON editor for any catalog entry lacking a hand-written form, and several field types have correctness gaps.

### Conditions, branching & predicate logic (workflow builder)

This subsystem lets non-technical staff build filter/branch/trigger conditions without ever seeing JSON. The condition-builder UI edits a deliberately-flat model (a single ALL or ANY list of Field·Operator·Value rows), which jsonlogic-codec.ts serializes to a small JSONLogic dialect (var/==/!=/></>=/</<=/in/and/or/not) that predicate.ts evaluates at runtime. Fields, operators, and known enum values are all pickers driven by refs.ts (curated trigger fields + typed upstream-step outputs + workflow vars), and explain-expr.ts renders every predicate as a plain-English phrase reused across cards, lane headers, and the inspector. Branch steps get true/false "Then/Else" lanes computed by branch-paths.ts, and trigger-filter.ts special-cases the label-added trigger with a dedicated label picker merged into the generic condition AND-list. The design is intentionally lossy-but-safe: anything the flat model can't represent falls back to a read-only "Custom condition" JSON view rather than corrupting the predicate. The chief weaknesses are expressiveness ceilings (no nested groups, no mixed AND/OR, no NOT-of-group, no field-to-field comparison, no date/contains/starts-with operators) and several correctness gaps in numeric/empty/type coercion that can make a condition evaluate differently than its English explanation implies.

**Limitations**

- [high] **No nested groups and no mixed AND/OR — the model is structurally flat** — ConditionModel is a single combine ('all'|'any') over a flat Clause[] (jsonlogic-codec.ts:37-40). There is no way to express '(A and B) or C'. parseCondition only accepts a top-level and/or whose every child is a leaf clause; any nested and/or inside an arm makes parseClause return null and the whole expression drops to read-only JSON mode (jsonlogic-codec.ts:83-95, 97-169). For real hotel automations ('priority is urgent AND (status is todo OR status is blocked)') this is a hard ceiling that silently forces non-technical users into a JSON view they were explicitly designed never to see. _(`lib/workflows/jsonlogic-codec.ts:37-40,83-95`)_
- [high] **No field-to-field comparison and no operand-on-the-left support** — serializeClause always builds {op:[{var:path}, literal]} — the right side is always a typed-in/coerced literal (jsonlogic-codec.ts:204-206). parseClause requires args[0] to be the var and the literal on the right for ==/!=/></>= (jsonlogic-codec.ts:153). There is no UI to compare two fields (e.g. 'due_at < now', or 'new status != previous status' on task.status_changed where both trigger.from and trigger.to exist). The evaluator and explain layer support var-on-either-side, but the builder cannot produce or round-trip it, so any such predicate becomes read-only JSON. _(`lib/workflows/jsonlogic-codec.ts:153,204-206`)_
- [high] **String 'is empty' silently changes meaning for numbers/booleans and 'is not empty' is broken for 0/false** — 'is empty' emits {not:{var}} and 'is not empty' emits {'!=':[var,'']}. For a number field whose value is 0, {not:{var}} is true (0 is falsy) so 'is empty' matches a present-zero value; and {'!=':[0,'']} is true under JS loose-equality oddities only sometimes — 0 != '' is true, so a 0 reads as 'not empty', contradicting the 'is empty' result for the same field. The codec's own comment acknowledges 0/'' ambiguity for bare var but still offers 'empty'/'not_empty' for number and boolean types (CLAUSE_OPS types include 'number','boolean' at jsonlogic-codec.ts:58-63), so a non-technical user gets results that contradict the English label. _(`lib/workflows/jsonlogic-codec.ts:58-63,187-189; lib/workflows/predicate.ts:39-42,67-68`)_
- [high] **Numeric comparison coerces both sides with Number(), so date-string and non-numeric comparisons silently become NaN-false** — evalNode for >,>=,<,<= does Number(a) and Number(b) unconditionally (predicate.ts:43-54). Due dates (trigger.new.due_at) and scheduled times are ISO strings; comparing them numerically yields NaN and every comparison returns false. The builder offers >,>=,<,<= only for type 'number', but due_at/fired_at are typed 'string' in refs.ts (refs.ts:91,113-119) so they only get ==/!=, meaning users literally cannot build a 'due date is before X' filter at all — and if such a predicate is authored in JSON it evaluates to constant-false rather than erroring. _(`lib/workflows/predicate.ts:43-54; lib/workflows/refs.ts:91,113-119`)_
- [high] **predicate.ts throws on unknown operators / multi-key objects at runtime instead of failing soft** — evalNode throws for any object with !=1 key (predicate.ts:26-28) and for any unrecognized operator (predicate.ts:69-70). A JSON-mode 'Custom condition' the builder accepted as opaque (e.g. one using a jsonlogic op like 'cat', 'if', '%', 'merge', '<=' chains of 3 args) will hard-throw at dispatch/filter time (dispatcher.ts:103, instant-runtime.ts:177). The builder happily preserves such expressions as read-only (parseCondition returns null -> JSON mode) yet the runtime cannot evaluate them, so a workflow can be saved in a state that crashes when it fires. _(`lib/workflows/predicate.ts:26-28,69-70`)_
- [medium] **No NOT-of-group / no negated conditions beyond 'is empty'** — The builder offers no 'none of' / 'does not contain' / negated-group operator. The codec only ever emits {not:{var}} for the 'is empty' case (jsonlogic-codec.ts:187-189); a real {not:{and:[...]}} predicate parses to null and falls to JSON mode. Combined with the missing 'any of' for scalar non-enum fields having no 'is none of' inverse, users cannot build common exclusion filters ('label is NOT vip') except via a single '!=' row, which doesn't generalize to lists. _(`lib/workflows/jsonlogic-codec.ts:50-68,183-207`)_
- [medium] **Equality uses JS loose == with no type coercion of the var side, so typed values mismatch** — evalNode '==' returns evalNode(a) == evalNode(b) using loose equality (predicate.ts:35-38). The right side is coerced by the codec to a real number/boolean for number/boolean fields (jsonlogic-codec.ts:233-240), but for enum/string fields the literal stays a string while the actual runtime payload value's type is whatever the event carries. Loose == papers over some cases (e.g. number 5 == '5') but not others (boolean true == 'true' is false). Because coerce() runs only at serialize time off the builder-inferred type, a field mis-typed in refs.ts (everything not explicitly enumerated defaults to 'json' in zodType, refs.ts:139-154) compares as a raw string and can never match a boolean/number payload. _(`lib/workflows/predicate.ts:35-38; lib/workflows/jsonlogic-codec.ts:233-240`)_
- [medium] **No 'contains' / 'starts with' / substring operator for free text** — The operator set has no text-contains. The evaluator's 'in' does support substring (predicate.ts:55-61: string haystack includes), but the codec never emits {in:[needle, stringVar]} for a free-text field — its 'is_any_of' for string[] emits needle-in-array, and for scalar strings it emits value-in-list. So a staff member cannot build 'message text contains refund', a very common chat-trigger need, despite the runtime being capable of it. _(`lib/workflows/jsonlogic-codec.ts:191-203; lib/workflows/predicate.ts:55-61`)_
- [medium] **Branch lane walk stops at the first nested branch and can't introspect grandchild branches** — Both walkPath and stepIdsOnPath break as soon as they hit a step with 'branches' (branch-paths.ts:37-38,77-78). A branch nested inside a Then-lane is treated as a terminal node, so its lane's stepCount/preview stops there and findStepBranchContext won't attribute steps on the inner branch's lanes to the outer branch. Nested branch UIs (the lane chips) under-report step counts and the 'View on canvas' deep-link may point at an incomplete chain. _(`lib/workflows/branch-paths.ts:37-38,71-82`)_
- [medium] **Three-arg comparison chains accepted by some jsonlogic authors are not handled; codec/explain only handle 2-arg** — parseClause and explain-expr require args.length===2 for comparisons (jsonlogic-codec.ts:151, explain-expr.ts:71). Standard JSONLogic permits {'<':[0, var, 100]} for between-bounds. Such an expression parses to null (JSON mode) in the builder and, at runtime, predicate.ts destructures only [a,b] (predicate.ts:47) silently ignoring the third operand — giving a wrong result with no error. _(`lib/workflows/predicate.ts:47; lib/workflows/jsonlogic-codec.ts:151`)_
- [medium] **Boolean field value coercion has no neutral/unset state and defaults to false** — coerce for boolean returns raw === 'true' (jsonlogic-codec.ts:238), and the boolean ValueInput defaults the displayed value to 'true' (condition-builder.tsx:929) but a freshly added boolean clause has value '' which coerces to false. So an untouched boolean condition reads as 'Yes' in the dropdown yet serializes to false until the user re-selects — a mismatch between what's shown and what's stored. _(`lib/workflows/jsonlogic-codec.ts:238; components/workflows/builder/config/condition-builder.tsx:924-936`)_
- [medium] **'now' and 'context' scope roots validate but aren't resolvable by the evaluator's varLookup** — validateScopeRef accepts head 'now' (predicate-vars.ts:66) and 'context', but predicate.ts varLookup only resolves trigger/steps/vars/context and returns undefined for 'now' (predicate.ts:74-82). A predicate using {var:'now'} passes validation but always reads undefined at runtime, so any time-based condition a user might hand-author is silently inert. _(`lib/workflows/predicate-vars.ts:66; lib/workflows/predicate.ts:74-82`)_
- [low] **is_any_of on a free-text (no-options) string field is fragile comma-splitting with no trim-on-store** — When a string field has no options[], 'is any of' falls back to a single input whose value is value.split(',').map(trim) on every keystroke (condition-builder.tsx:889-903). Typing 'a, b,' yields a trailing empty value; the serializer filters empties (jsonlogic-codec.ts:192) but the round-tripped model can momentarily show stray chips, and there is no escaping for values that legitimately contain commas (e.g. a label literally named 'a,b'). _(`components/workflows/builder/config/condition-builder.tsx:889-903; lib/workflows/jsonlogic-codec.ts:191-192`)_

### Workflow editor — Step catalog, field definitions & data refs

The catalog is a pure-metadata vocabulary layer (client-safe; runners live elsewhere) that describes 18 triggers and ~30 step types across tasks/chat/docs/meetings/calendar/entities/system/ai/control surfaces. Each entry carries label, plain-English description, examplePrompts (the AI bot's vocabulary), a Zod outputSchema, and an explain() summarizer. field-defs.ts declares per-step typed form fields (template/text/textarea/enum/number/duration/string-list/key-value/channel) so the inspector renders friendly forms instead of raw JSON, and refs.ts builds the data picker by combining curated trigger fields + upstream-step outputSchema keys + workflow variables, never exposing {{dotted.path}} to users. The design is coherent and the UX intent (no magic strings, enum-aware dropdowns, humanized labels) is strong. However coverage is uneven: several catalog steps/triggers lack field-defs (forcing a JSON fallback), the data-ref model breaks for loops/parallel/extract_fields, and the integration breadth is internal-only — no HTTP/webhook/email/SMS/transform primitives, which caps what non-technical staff can automate without delegating to the not-yet-built OpenClaw tier.

### Workflow builder — spec model, validation, graph, persistence

The spec layer is a single Zod-defined WorkflowSpec (lib/workflows/spec.ts) — a versioned trigger + a keyed map of discriminated-union step nodes with `next`/`branches`/`on_error` edges, plus optional variables and canvas layout. Validation (validate.ts) runs four passes: Zod parse, catalog membership, template-ref reachability via a BFS upstream map, and JSONLogic predicate var-path checks (predicate-vars.ts). graph.ts is a pure spec↔node/edge bridge for the xyflow "Map" view with auto-layout and CRUD mutators; rename-step.ts rewrites a step id and all references; resolve.ts performs the runtime template substitution that mirrors validation pass 3. save.ts validates, hashes, writes an immutable workflow_versions row, flips current_version_id, and reconciles pg_cron. BuilderShell owns in-memory spec + saved baseline + an AI-unaccepted diff set, with debounced silent autosave and a Flow/Map toggle. The model is well-factored and the validator is genuinely thoughtful, but autosave/versioning, concurrency, and several reachability/edge-integrity rules have real gaps.

**Limitations**

- [high] **Disconnecting the trigger edge produces an unsaveable spec with no user-visible reason** — graph.disconnect and removeStep set `entry_step_id: ""` when the trigger edge or entry step is removed (graph.ts:307,374). But the spec schema requires `entry_step_id: z.string().min(1)` (spec.ts:493), so the resulting spec fails Zod parse. Autosave silently bails (`if (!validateSpec(debouncedSpec).ok) return`, builder-shell.tsx:95) and the inline per-step validator only surfaces issues with a `step_id` (computeInvalid skips the `entry_step_id` path issue, builder-shell.tsx:293-296). The user disconnects the trigger, sees 'Fix the errors above to save' with no error pinned to any card, and silently loses all subsequent edits. _(`lib/workflows/graph.ts:307,374; lib/workflows/spec.ts:493; components/workflows/builder/builder-shell.tsx:95,293-296`)_
- [high] **Every canvas node drag creates a new immutable workflow version** — applyPositionsToSpec returns a new spec object embedding `layout` (graph.ts:256-261). `dirty` is reference equality (builder-shell.tsx:52) so any position change marks dirty and, after debounce, autosaves. spec_hash is computed over the whole canonical spec including `layout` (save.ts:42-43), so a pure cosmetic reposition is NOT deduped — it writes a brand-new workflow_versions row and flips current_version_id. Rearranging nodes spams the version history with semantically-identical rows and bumps the running version. Layout should be excluded from the hash (or persisted separately from versioned spec). _(`lib/workflows/graph.ts:256-261; lib/workflows/save.ts:42-43; components/workflows/builder/builder-shell.tsx:52,90-102`)_
- [high] **No concurrency control — last write wins, silently clobbering a concurrent editor or stale tab** — saveWorkflow computes nextVersion from the latest version row and updates workflows by id+property_id with no optimistic-lock / expected-version check (save.ts:46-75,94-100). Two editors (or a forgotten background tab whose autosave fires) both PATCH; the second overwrites the first with no conflict detection. The client never sends a base version and the server never compares one. For a multi-staff product this loses edits silently. _(`lib/workflows/save.ts:46-75,94-100; app/api/properties/[propertyId]/workflows/[workflowId]/route.ts:48-86`)_
- [medium] **No unsaved-changes / in-flight-save guard on navigation** — BuilderShell autosaves on a 1200ms debounce but has no beforeunload handler and no block on navigating away while `dirty && !saving` or while a save is in flight. A user who edits and immediately closes the tab (or navigates within the SPA) within the debounce window loses the edit with no warning. The 'All changes saved.' status can also be stale relative to debounced/pending state. _(`components/workflows/builder/builder-shell.tsx:51-102,151-159`)_
- [medium] **Validation never checks for cycles or unreachable (orphan) steps as errors** — buildUpstreamMap has cycle protection for traversal (validate.ts:246-253) but validateSpec never reports a cycle, and orphan steps unreachable from entry_step_id are silently tolerated — the only handling is graph.autoLayout dumping them into a trailing column (graph.ts:113-118). A workflow with a `next` loop or a stranded sub-chain validates `ok` and saves; the executor's behavior on a cycle is undefined. Non-technical users get no signal that part of their flow can never run. _(`lib/workflows/validate.ts:232-267; lib/workflows/graph.ts:113-118`)_
- [medium] **Control-flow target fields (foreach.body_start, parallel.branches, switch keys) are not existence-validated** — passReferences only checks `step.next` and `step.branches.*` targets (validate.ts:94-115). foreach.config.body_start and parallel.config.branches[] are plain strings (spec.ts:398-415) that point at step ids but are never checked against spec.steps, so a foreach whose body_start references a deleted/nonexistent step validates clean and saves. Likewise removeStep sweeps `next`/`branches`/`on_error` but never rewrites a foreach body_start or parallel branch that pointed at the removed step (graph.ts:339-376), leaving a dangling pointer. _(`lib/workflows/validate.ts:94-115; lib/workflows/spec.ts:398-415; lib/workflows/graph.ts:339-376`)_
- [medium] **Upstream/reference validation ignores loop and parallel edges, producing false 'not upstream' errors** — The code comment admits buildUpstreamMap 'ignores loop/parallel edges' (validate.ts:88-91). buildUpstreamMap only traverses `next` and `branches` (validate.ts:255-264); it does NOT follow foreach.body_start or parallel.branches. So a step inside a foreach body that legitimately references {{steps.<upstream>.output}} from before the loop, or any step reached only via a parallel/foreach edge, has an empty/incomplete predecessor set and validateRef wrongly reports 'Step X is not upstream' — blocking save on a valid workflow. (Note graph.autoLayout DOES follow these edges at graph.ts:103-110, so the two traversals disagree.) _(`lib/workflows/validate.ts:255-264; lib/workflows/graph.ts:103-110; lib/workflows/validate.ts:222-226`)_
- [low] **branch_switch `_default` and switch values are validated as step targets but resolution/coverage is not** — BranchSwitchStep.branches is z.record(string,string) with a documented but unenforced `_default` convention (spec.ts:371-378). There is no validation that a switch has a `_default` or any exhaustiveness, and the graph renders every key as a branch edge including `_default` as a literal label (graph.ts:217-231). A switch with no matching case and no `_default` will silently dead-end at runtime with no save-time warning (unlike branch_if/filter which DO warn on empty expr). _(`lib/workflows/spec.ts:371-378; lib/workflows/validate.ts:159-200; lib/workflows/graph.ts:217-231`)_
- [low] **Template-ref validation only inspects config strings, missing trigger.entity_type, variable defaults, and branch_switch labels** — passReferences walks `step.config` only (validate.ts:119-136). Refs are common in config so this is mostly covered, but {{...}} inside spec.variables[*].default (VariableDecl.default is z.unknown, spec.ts:472-476) and in trigger entity_type are never checked, and resolve.ts does not resolve variable defaults either — a default like {{trigger.x}} would never be substituted. Minor but an inconsistency between what validates and what resolves. _(`lib/workflows/validate.ts:119-136; lib/workflows/spec.ts:472-476; lib/workflows/resolve.ts:20-31`)_
- [low] **computeInvalid runs the full validateSpec on every keystroke for inline card errors** — computeInvalid (builder-shell.tsx:272-299) calls validateSpec(spec) which itself rebuilds the upstream map and re-parses; it is memoized on `spec` (builder-shell.tsx:127) but `canPersist` also calls validateSpec(spec) independently (builder-shell.tsx:54), so each spec change runs the full multi-pass validator at least twice. For large workflows this is wasteful re-computation on every edit; a single memoized ValidationResult could feed both. _(`components/workflows/builder/builder-shell.tsx:54,127,272-299`)_
- [low] **spec.ts duration/cron regex is permissive and at_time is not range-checked** — DelayStep duration regex `/^\d+\s*(s|m|h|d)$/` accepts '0s' and arbitrarily large values with no upper bound (spec.ts:384); schedule.at can be any past ISO datetime (spec.ts:57) with no validation that it is in the future, so a schedule.at_time trigger set to the past saves cleanly and either never fires or fires immediately depending on the dispatcher. cron string is unvalidated (z.string()) at the schema layer (spec.ts:54); an invalid cron only fails later at the pg_cron RPC during save. _(`lib/workflows/spec.ts:54,57,384`)_

### Workflow runtime / execution engine & run observability

Two execution paths share a near-identical graph walker: instant-runtime.ts runs in-process for short/synchronous workflows; durable-runtime.ts runs inside the Vercel Workflow SDK ("use workflow"/"use step") for delay/wait/loop/parallel workflows, with sleep/createHook primitives for durability. The dispatcher (dispatcher.ts) maps a workflow_event to matching enabled workflows, evaluates trigger predicates, records why each was skipped, routes by classifyMode, and auto-resumes durable waits correlated to the event. Step results are persisted to workflow_step_runs and surfaced in a read-only run inspector that live-tails via Supabase Realtime, with a humanizeStepError() layer that translates known runtime messages into plain English — genuinely the strongest part of the observability story for non-technical users. However the observability surface has serious gaps: there is no real test/dry-run UI (dryRun is fully plumbed through every runner but never reachable from the builder), no cancel/replay/retry-single-step capability, step rows are written only at completion so the "live" inspector never shows a step actually in progress and step durations are meaningless, and several status/error fields the schema and UI reference (filtered for steps, error_step_id, cancelled, ai_trace, waiting) are never written by the runtime — so the inspector promises detail the engine doesn't produce.

**Files reviewed:** `lib/workflows/dispatcher.ts`, `lib/workflows/durable-runtime.ts`, `lib/workflows/instant-runtime.ts`, `lib/workflows/event-emitter.ts`, `lib/workflows/runners/index.ts`, `lib/workflows/runners/types.ts`, `lib/workflows/runners/ai.ts`, `lib/workflows/runners/tasks.ts`, `lib/workflows/runners/chat.ts`, `lib/workflows/runners/notify.ts`, `lib/workflows/runners/system.ts`, `components/workflows/workflow-runs.tsx`, `components/workflows/workflow-run-detail.tsx`, `components/workflows/all-runs.tsx`, `app/p/[propertyId]/workflows/[workflowId]/runs/[runId]/run-inspector-client.tsx`, `app/api/properties/[propertyId]/workflows/[workflowId]/run/route.ts`, `app/api/properties/[propertyId]/workflows/[workflowId]/runs/[runId]/route.ts`, `lib/query/workflow-queries.ts`, `supabase/migrations/0026_workflows.sql`

### Workflows — AI copilot, templates, and entry/list surfaces (first-run authoring & navigation)

This subsystem is the "zero to working automation" path: an AI copilot that turns plain-English goals into a WorkflowSpec, a starter-prompt new-workflow screen, a template gallery you can fork, and a workflows list with search/filter/enable-toggle plus route-based tab navigation. The copilot (ai-copilot.tsx) POSTs to /workflows/author, which runs a Tier-1 author bot (workflow-author-bot.ts) that introspects the step catalog via tools and emits a validated spec, or returns a clarification / entity-type proposal / error. The architecture is clean and non-technical-user-aware in many places (plain-English narration enforced in the bot's guidelines, friendly mode badges, optimistic enable/delete with rollback, good empty states). However the authoring loop has several real holes: the bot's propose_entity_type branch is a dead-end with no UI wired anywhere, conversation history is sent in a shape the bot can't consume, starter prompts silently swallow clarifications and errors, and there is no streaming or cancel despite the UI implying both. The list/template/tabs surfaces are solid but have a few discoverability and consistency gaps.
